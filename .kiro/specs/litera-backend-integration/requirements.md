# Документ требований: litera-backend-integration

## Introduction

Проект «ЛитЭра» — книжный трекер с бэкендом на FastAPI и фронтендом на Vanilla JS. Бэкенд частично реализован: есть аутентификация, загрузка книг и трекинг прогресса чтения. Фронтенд содержит готовый UI, но работает на захардкоженных данных и не подключён к API.

Данная фича охватывает три направления:
1. **Доработка бэкенда** — новые модели (Shelf, BookNote, ReadingSession, ReadingGoal), новые эндпоинты, исправление существующих проблем безопасности и надёжности.
2. **Интеграция фронтенда** — замена всех захардкоженных данных на реальные вызовы API, добавление проверки авторизации на всех страницах.
3. **Безопасность и надёжность** — refresh-токены, rate limiting, Alembic-миграции, валидация файлов по содержимому, устранение утечки storage_key.

**Глоссарий:**
- **API** — бэкенд-сервис на FastAPI, доступный по HTTP.
- **Frontend** — клиентская часть на Vanilla HTML/CSS/JS.
- **JWT** — JSON Web Token, используется для аутентификации.
- **Access_Token** — краткосрочный JWT для авторизации запросов.
- **Refresh_Token** — долгосрочный токен для получения нового Access_Token без повторного входа.
- **MinIO** — S3-совместимое хранилище файлов книг.
- **Presigned_URL** — временная ссылка для прямого доступа к файлу в MinIO.
- **Shelf** — пользовательская коллекция книг (полка).
- **ShelfBook** — связь между Shelf и Book.
- **BookNote** — текстовая заметка пользователя к книге.
- **ReadingSession** — запись о сессии чтения с временными метками и количеством прочитанных страниц.
- **ReadingGoal** — цель пользователя по чтению (страниц в день или минут в день).
- **ReadingProgress** — текущий прогресс чтения книги (страница, процент, статус).
- **Alembic** — инструмент версионирования схемы базы данных для SQLAlchemy.
- **Rate_Limiter** — механизм ограничения частоты запросов.
- **CORS** — Cross-Origin Resource Sharing, политика браузера для межсайтовых запросов.
- **storage_key** — внутренний ключ файла в MinIO, не предназначенный для передачи клиенту.
- **Dashboard** — главная страница (index.html) со списком книг и виджетами.
- **Shelves_Page** — страница полок (shelves.html).
- **Reader_Page** — страница чтения книги (reader.html).

## Requirements

### Requirement 1: Система Refresh-токенов

**User Story:** Как пользователь, я хочу оставаться авторизованным без повторного ввода пароля, чтобы не прерывать работу с приложением каждые несколько часов.

#### Критерии приёмки

1. WHEN пользователь успешно входит в систему, THE API SHALL вернуть объект с полями `access_token` (срок действия 30 минут), `refresh_token` (срок действия 30 дней) и `token_type: "bearer"`.
2. WHEN клиент отправляет POST /auth/refresh с валидным `refresh_token` в теле запроса, THE API SHALL вернуть новый `access_token` и новый `refresh_token`.
3. IF `refresh_token` истёк или не существует в базе данных, THEN THE API SHALL вернуть HTTP 401 с сообщением "Сессия истекла, войдите снова".
4. WHEN пользователь вызывает POST /auth/logout с валидным `refresh_token`, THE API SHALL удалить запись refresh-токена из базы данных и вернуть HTTP 200.
5. THE Frontend SHALL сохранять `access_token` и `refresh_token` в `localStorage` после успешного входа.
6. WHEN Frontend получает HTTP 401 на любой защищённый запрос, THE Frontend SHALL автоматически вызвать POST /auth/refresh и повторить исходный запрос с новым `access_token`.
7. IF обновление токена завершилось ошибкой, THEN THE Frontend SHALL удалить оба токена из `localStorage` и перенаправить пользователя на страницу входа.
8. THE API SHALL хранить refresh-токены в таблице `refresh_tokens` с полями: `id`, `user_id`, `token_hash` (SHA-256), `expires_at`, `created_at`.

### Requirement 2: Alembic-миграции базы данных

**User Story:** Как разработчик, я хочу версионировать схему базы данных через Alembic, чтобы безопасно применять изменения в продакшне без потери данных.

#### Критерии приёмки

1. THE API SHALL использовать Alembic для управления схемой базы данных вместо `Base.metadata.create_all()` при старте.
2. THE Alembic SHALL содержать начальную миграцию, создающую таблицы `users`, `books`, `reading_progress`.
3. WHEN разработчик выполняет `alembic upgrade head`, THE Alembic SHALL применить все миграции без ошибок на чистой базе данных.
4. WHEN разработчик выполняет `alembic downgrade -1`, THE Alembic SHALL откатить последнюю миграцию без потери данных предыдущих версий.
5. THE Docker_Compose SHALL запускать `alembic upgrade head` как entrypoint перед стартом API-сервера.

### Requirement 3: Управление профилем пользователя

**User Story:** Как пользователь, я хочу изменять свои данные (имя, email, пароль) и удалять аккаунт, чтобы управлять своей учётной записью.

#### Критерии приёмки

1. WHEN авторизованный пользователь отправляет PATCH /auth/me с одним или несколькими полями (`username`, `email`, `password`), THE API SHALL обновить только переданные поля и вернуть обновлённый объект `UserOut`.
2. IF новый `username` или `email` уже занят другим пользователем, THEN THE API SHALL вернуть HTTP 400 с описанием конфликта.
3. WHEN пользователь меняет пароль, THE API SHALL принять поля `current_password` и `new_password`; IF `current_password` неверен, THEN THE API SHALL вернуть HTTP 400.
4. WHEN авторизованный пользователь отправляет DELETE /auth/me, THE API SHALL удалить аккаунт, все книги пользователя, файлы из MinIO, все refresh-токены и вернуть HTTP 204.
5. THE Frontend SHALL предоставить форму редактирования профиля, доступную через иконку пользователя в шапке.

### Requirement 4: Модель и API полок (Shelf)

**User Story:** Как пользователь, я хочу создавать именованные полки и добавлять на них книги, чтобы организовывать свою библиотеку.

#### Критерии приёмки

1. THE API SHALL поддерживать CRUD-операции для полок через эндпоинты: POST /shelves/, GET /shelves/, GET /shelves/{id}, PATCH /shelves/{id}, DELETE /shelves/{id}.
2. WHEN пользователь создаёт полку через POST /shelves/ с полем `name` (1–100 символов), THE API SHALL создать запись `Shelf` с полями `id`, `user_id`, `name`, `created_at` и вернуть HTTP 201.
3. WHEN пользователь отправляет POST /shelves/{id}/books с `book_id`, THE API SHALL добавить книгу на полку, создав запись `ShelfBook`, и вернуть HTTP 201.
4. IF книга уже находится на данной полке, THEN THE API SHALL вернуть HTTP 409 с сообщением "Книга уже на этой полке".
5. WHEN пользователь отправляет DELETE /shelves/{shelf_id}/books/{book_id}, THE API SHALL удалить книгу с полки и вернуть HTTP 204.
6. WHEN пользователь запрашивает GET /shelves/{id}, THE API SHALL вернуть полку вместе со списком книг на ней (включая `title`, `author`, `cover_url`).
7. IF пользователь пытается получить или изменить чужую полку, THEN THE API SHALL вернуть HTTP 403.
8. WHEN пользователь удаляет полку через DELETE /shelves/{id}, THE API SHALL удалить полку и все связи `ShelfBook`, но НЕ удалять сами книги.
9. THE Frontend SHALL загружать список полок из GET /shelves/ при открытии Shelves_Page вместо отображения захардкоженных данных.
10. THE Frontend SHALL отправлять POST /shelves/ при нажатии кнопки "Создать полку" в модальном окне.
11. THE Frontend SHALL отправлять POST /shelves/{id}/books при выборе "На полку" в контекстном меню книги.

### Requirement 5: Жанры книг

**User Story:** Как пользователь, я хочу указывать жанр при добавлении книги и фильтровать библиотеку по жанру, чтобы быстро находить нужные книги.

#### Критерии приёмки

1. THE API SHALL добавить поле `genre` (строка, максимум 100 символов, необязательное) в модель `Book` и соответствующую Alembic-миграцию.
2. WHEN пользователь загружает книгу через POST /books/ с полем `genre`, THE API SHALL сохранить жанр и вернуть его в `BookOut`.
3. WHEN пользователь запрашивает GET /books/my?genre=Детектив, THE API SHALL вернуть только книги с указанным жанром (регистронезависимое сравнение).
4. THE Frontend SHALL передавать выбранный жанр из модального окна добавления книги в запрос POST /books/.
5. THE Frontend SHALL использовать параметр `genre` в запросе GET /books/my при выборе жанра в панели сортировки вместо клиентской фильтрации.

### Requirement 6: Пагинация и поиск книг

**User Story:** Как пользователь с большой библиотекой, я хочу получать книги постранично и искать по названию или автору, чтобы интерфейс оставался быстрым.

#### Критерии приёмки

1. WHEN пользователь запрашивает GET /books/my?page=1&page_size=20, THE API SHALL вернуть объект с полями `items` (список книг), `total` (общее количество), `page`, `page_size`.
2. THE API SHALL использовать значения по умолчанию `page=1`, `page_size=20` при отсутствии параметров.
3. IF `page_size` превышает 100, THEN THE API SHALL вернуть HTTP 422 с описанием ограничения.
4. WHEN пользователь запрашивает GET /books/search?q=Мастер, THE API SHALL вернуть книги, у которых `title` или `author` содержат подстроку "Мастер" (регистронезависимо), с поддержкой пагинации.
5. THE Frontend SHALL реализовать поиск через GET /books/search при вводе текста в поле поиска в шапке (с задержкой debounce 300 мс).

### Requirement 7: Заметки к книгам (BookNote)

**User Story:** Как пользователь, я хочу добавлять текстовые заметки к книгам, чтобы фиксировать мысли во время чтения.

#### Критерии приёмки

1. THE API SHALL поддерживать CRUD для заметок: POST /books/{id}/notes, GET /books/{id}/notes, PATCH /books/{id}/notes/{note_id}, DELETE /books/{id}/notes/{note_id}.
2. WHEN пользователь создаёт заметку через POST /books/{id}/notes с полем `text` (1–5000 символов), THE API SHALL создать запись `BookNote` с полями `id`, `user_id`, `book_id`, `text`, `created_at`, `updated_at` и вернуть HTTP 201.
3. IF пользователь пытается создать заметку к чужой книге, THEN THE API SHALL вернуть HTTP 403.
4. THE Frontend SHALL отображать существующие заметки и форму добавления заметки при нажатии на ссылку "Добавьте заметку" в карточке книги.
5. WHEN пользователь добавляет заметку при загрузке книги через модальное окно, THE Frontend SHALL передать текст заметки в POST /books/{id}/notes после успешного создания книги.

### Requirement 8: Сессии чтения (ReadingSession)

**User Story:** Как пользователь, я хочу, чтобы приложение автоматически фиксировало время и страницы каждой сессии чтения, чтобы видеть реальную статистику.

#### Критерии приёмки

1. THE API SHALL поддерживать создание сессий чтения через POST /books/{id}/sessions с полями `started_at`, `ended_at`, `pages_read`.
2. THE API SHALL хранить сессии в таблице `reading_sessions` с полями: `id`, `user_id`, `book_id`, `started_at`, `ended_at`, `pages_read`, `duration_minutes`.
3. WHEN клиент отправляет POST /books/{id}/sessions, THE API SHALL вычислить `duration_minutes` как разницу между `ended_at` и `started_at` в минутах и сохранить значение.
4. IF `ended_at` раньше `started_at`, THEN THE API SHALL вернуть HTTP 422 с сообщением "Время окончания не может быть раньше времени начала".
5. THE Frontend SHALL автоматически создавать сессию чтения при закрытии Reader_Page, отправляя время открытия страницы, время закрытия и количество прочитанных страниц.

### Requirement 9: Статистика чтения

**User Story:** Как пользователь, я хочу видеть реальную статистику своего чтения (страниц за период, динамику), чтобы отслеживать прогресс.

#### Критерии приёмки

1. WHEN пользователь запрашивает GET /stats/reading?period=week, THE API SHALL вернуть объект с полями: `total_pages` (сумма страниц за период), `total_minutes` (сумма минут), `sessions_count`, `daily_breakdown` (массив объектов `{date, pages, minutes}` за каждый день периода).
2. THE API SHALL поддерживать значения параметра `period`: `week` (7 дней), `month` (30 дней), `year` (365 дней).
3. IF параметр `period` не входит в допустимые значения, THEN THE API SHALL вернуть HTTP 422.
4. THE Frontend SHALL загружать статистику из GET /stats/reading?period=week при открытии виджета статистики в шапке и отображать реальные данные вместо захардкоженных "452 стр" и "+12%".
5. WHEN пользователь переключает вкладки "7 дней" / "Месяц" / "Год" в виджете статистики, THE Frontend SHALL повторно запрашивать GET /stats/reading с соответствующим параметром `period`.
6. THE Frontend SHALL строить SVG-график активности на основе поля `daily_breakdown` из ответа API.

### Requirement 10: Цели чтения (ReadingGoal)

**User Story:** Как пользователь, я хочу устанавливать ежедневные цели по количеству страниц и времени чтения, чтобы поддерживать читательскую дисциплину.

#### Критерии приёмки

1. THE API SHALL поддерживать управление целями через POST /goals/ и GET /goals/ для создания и получения целей пользователя.
2. WHEN пользователь создаёт цель через POST /goals/ с полями `goal_type` (`pages_per_day` или `minutes_per_day`) и `target_value` (целое число > 0), THE API SHALL сохранить цель и вернуть HTTP 201.
3. THE API SHALL хранить цели в таблице `reading_goals` с полями: `id`, `user_id`, `goal_type`, `target_value`, `created_at`.
4. WHEN пользователь запрашивает GET /goals/, THE API SHALL вернуть список активных целей пользователя вместе с полем `current_value` — фактическим значением за текущий день на основе данных из `reading_sessions`.
5. THE Frontend SHALL загружать цели из GET /goals/ при открытии виджета профиля в шапке и отображать реальные значения вместо захардкоженных "452" и "40 м".
6. WHEN пользователь нажимает кнопку редактирования цели (✏) в виджете, THE Frontend SHALL отправить POST /goals/ с новым значением.

### Requirement 11: Обложки книг

**User Story:** Как пользователь, я хочу видеть обложки книг в своей библиотеке, чтобы визуально ориентироваться в коллекции.

#### Критерии приёмки

1. THE API SHALL добавить поле `cover_key` (строка, необязательное) в модель `Book` для хранения ключа обложки в MinIO.
2. THE API SHALL добавить эндпоинт POST /books/{id}/cover для загрузки изображения обложки (JPEG или PNG, максимум 5 МБ).
3. WHEN пользователь загружает обложку через POST /books/{id}/cover, THE API SHALL сохранить файл в MinIO с ключом вида `covers/{user_id}/{book_id}.jpg` и обновить поле `cover_key` в записи книги.
4. IF загружаемый файл не является JPEG или PNG по содержимому (magic bytes), THEN THE API SHALL вернуть HTTP 415 с сообщением "Поддерживаются только форматы JPEG и PNG".
5. THE API SHALL включать поле `cover_url` (Presigned_URL для обложки или `null`) в ответ `BookOut`.
6. THE Frontend SHALL отображать `cover_url` из API в карточках книг вместо статичных изображений-заглушек.

### Requirement 12: Устранение утечки storage_key

**User Story:** Как администратор безопасности, я хочу, чтобы внутренние ключи хранилища не передавались клиенту, чтобы предотвратить несанкционированный доступ к файлам.

#### Критерии приёмки

1. THE API SHALL удалить поле `storage_key` из схемы `BookOut` и всех ответов эндпоинтов книг.
2. THE API SHALL возвращать только `presigned_url` для доступа к файлу книги; `storage_key` SHALL использоваться исключительно во внутренней логике сервера.
3. WHEN клиент запрашивает GET /books/my или GET /books/{id}, THE API SHALL не включать `storage_key` в JSON-ответ.

### Requirement 13: Безопасность CORS

**User Story:** Как администратор безопасности, я хочу ограничить список разрешённых источников для CORS, чтобы предотвратить межсайтовые атаки в продакшне.

#### Критерии приёмки

1. THE API SHALL читать список разрешённых CORS-источников из переменной окружения `ALLOWED_ORIGINS` (разделённых запятой).
2. WHILE переменная `ALLOWED_ORIGINS` не задана, THE API SHALL использовать значение по умолчанию `http://localhost:3000,http://localhost:5500,http://127.0.0.1:5500`.
3. THE API SHALL заменить `allow_origins=["*"]` на список из переменной окружения `ALLOWED_ORIGINS`.
4. THE Frontend SHALL вынести `API_BASE_URL` в отдельный конфигурационный файл `js/config.js`, который подключается первым на всех страницах.
5. WHERE переменная `API_BASE_URL` не задана в `config.js`, THE Frontend SHALL использовать значение по умолчанию `http://localhost:8000`.

### Requirement 14: Rate Limiting для аутентификации

**User Story:** Как администратор безопасности, я хочу ограничить количество попыток входа с одного IP-адреса, чтобы защитить систему от брутфорс-атак.

#### Критерии приёмки

1. THE API SHALL ограничивать количество запросов к POST /auth/login до 10 запросов в минуту с одного IP-адреса.
2. IF количество запросов к POST /auth/login с одного IP превышает 10 в минуту, THEN THE API SHALL вернуть HTTP 429 с заголовком `Retry-After` и значением количества секунд до сброса лимита.
3. THE API SHALL ограничивать количество запросов к POST /auth/register до 5 запросов в минуту с одного IP-адреса.
4. THE API SHALL реализовать rate limiting через библиотеку `slowapi` с хранением счётчиков в памяти процесса.

### Requirement 15: Валидация файлов книг по содержимому

**User Story:** Как пользователь, я хочу получать понятную ошибку при загрузке файла неверного формата, чтобы не тратить время на ожидание загрузки некорректного файла.

#### Критерии приёмки

1. WHEN пользователь загружает файл через POST /books/, THE API SHALL проверить первые 8 байт файла (magic bytes) для определения реального формата.
2. IF реальный формат файла не соответствует заявленному параметру `format`, THEN THE API SHALL вернуть HTTP 415 с сообщением "Содержимое файла не соответствует указанному формату".
3. THE API SHALL проверять следующие сигнатуры: PDF (`%PDF`), EPUB (ZIP-заголовок `PK\x03\x04`), FB2 (XML-заголовок `<?xml` или `<FictionBook`).
4. IF расширение файла не входит в список `.pdf`, `.epub`, `.fb2`, THEN THE API SHALL вернуть HTTP 415 до проверки содержимого.

### Requirement 16: Параллельная генерация Presigned URL

**User Story:** Как пользователь с большой библиотекой, я хочу, чтобы список книг загружался быстро, чтобы не ждать последовательной генерации ссылок для каждой книги.

#### Критерии приёмки

1. WHEN API обрабатывает GET /books/my, THE API SHALL генерировать Presigned_URL для всех книг параллельно с использованием `asyncio.gather`.
2. IF генерация Presigned_URL для отдельной книги завершилась ошибкой, THE API SHALL установить `presigned_url: null` для этой книги и продолжить обработку остальных книг.
3. THE API SHALL завершить обработку GET /books/my не более чем за 3 секунды при наличии до 100 книг в библиотеке пользователя.

### Requirement 17: Проверка авторизации на фронтенде

**User Story:** Как пользователь, я хочу автоматически перенаправляться на страницу входа при попытке открыть защищённые страницы без авторизации, чтобы мои данные были защищены.

#### Критерии приёмки

1. WHEN пользователь открывает index.html, shelves.html или reader.html без `access_token` в `localStorage`, THE Frontend SHALL немедленно перенаправить пользователя на log.html.
2. THE Frontend SHALL выполнять проверку авторизации как первое действие при загрузке каждой защищённой страницы (до любых API-запросов).
3. WHEN пользователь нажимает кнопку выхода, THE Frontend SHALL вызвать POST /auth/logout, удалить оба токена из `localStorage` и перенаправить на log.html.

### Requirement 18: Загрузка книг на Dashboard из API

**User Story:** Как пользователь, я хочу видеть свои реальные книги на главной странице, а не захардкоженные примеры, чтобы работать со своей библиотекой.

#### Критерии приёмки

1. WHEN пользователь открывает index.html, THE Frontend SHALL загрузить список книг из GET /books/my и динамически отрисовать карточки книг вместо статичного HTML.
2. THE Frontend SHALL отображать для каждой книги: `title`, `author`, `genre`, `cover_url` (или заглушку при `null`), прогресс чтения из ReadingProgress, дату последнего открытия.
3. WHEN пользователь нажимает кнопку "Добавить книгу" и заполняет форму, THE Frontend SHALL отправить multipart/form-data запрос POST /books/ с файлом, названием, автором, жанром и заметкой.
4. WHEN пользователь нажимает "Удалить" в контекстном меню книги, THE Frontend SHALL вызвать DELETE /books/{id} и удалить карточку из DOM после успешного ответа.
5. WHEN пользователь нажимает кнопку воспроизведения на карточке книги, THE Frontend SHALL перейти на reader.html?book_id={id}.
6. IF GET /books/my вернул пустой список, THE Frontend SHALL отобразить сообщение "Ваша библиотека пуста. Добавьте первую книгу!" вместо пустого списка.

### Requirement 19: Блок "Продолжите чтение"

**User Story:** Как пользователь, я хочу видеть на главной странице книгу, которую читаю прямо сейчас, чтобы быстро продолжить чтение.

#### Критерии приёмки

1. WHEN пользователь открывает index.html, THE Frontend SHALL запросить GET /books/my и найти книгу со статусом `reading` и наибольшим значением `last_read_at`.
2. THE Frontend SHALL отобразить в блоке "Продолжите чтение" название найденной книги, обложку и процент прочтения.
3. IF ни одна книга не имеет статуса `reading`, THE Frontend SHALL скрыть блок "Продолжите чтение".

### Requirement 20: Конфигурация API_BASE_URL на фронтенде

**User Story:** Как разработчик, я хочу иметь единое место для настройки адреса API, чтобы не менять URL в каждом файле при смене окружения.

#### Критерии приёмки

1. THE Frontend SHALL содержать файл `js/config.js` с константой `API_BASE_URL`, подключаемый первым тегом `<script>` на всех HTML-страницах.
2. THE Frontend SHALL удалить дублирующее объявление `const API_BASE_URL` из файла `js/api.js` и использовать значение из `js/config.js`.
3. THE Frontend SHALL использовать `API_BASE_URL` из `js/config.js` во всех fetch-запросах на всех страницах.
